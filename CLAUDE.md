# CLAUDE.md

This file provides guidance to AI coding assistants when working with code in this repository.

## Repository Overview

This repository contains the digital infrastructure for **Ortex Industries** (manufacturer of customized MDF/acrylic items, lanyards, corporate gifts, OEM/white-label production). It is split into four **independent npm projects** (no root workspace); the root `README.md` has the full directory tree and conventions.

1. **`Ortex.Web`**: The marketing/lead-gen single-page app (React 19 + Vite 8 + Tailwind CSS v4). Brand showcase, product catalog, quote wizard, lead capture, Live Orty voice assistant.
2. **`Ortex.Admin`**: The business admin dashboard (React 19 + Vite 8 + Tailwind CSS v4 + Supabase). Manages leads, quotations, invoices, payments, customers, catalogue, social, automation and the AI telecaller. Owns the Supabase schema (`supabase/migrations`) and Deno edge functions (`supabase/functions`).
3. **`Ortex.Mobile`**: The field-sales mobile app (React Native 0.85 bare workflow + Expo SDK 56 modules + TypeScript). Quotations, enquiries, voice leads, products and a call/WhatsApp contact directory. It is a **second client of Ortex.Admin's Supabase project**, same anon key, same session, same `profiles` roles and RLS, and owns no edge function of its own. It has needed exactly one schema change (`0021_profile_phone.sql`, a `phone` column on `profiles` for its Account details page); migrations still live in `Ortex.Admin/supabase/migrations` and are pushed from there. Its `src/domain/` is a line-for-line **mirror** of the Admin's pure logic (see below); `npm test` fails if the two GST engines drift apart.
4. **`Ortex.Tally.Connector`**: A **standalone** Node CLI (outbound: Admin → Tally). It is not imported or launched by `Ortex.Admin`. It must run on the Windows PC where TallyPrime is open, because Tally's XML gateway only listens on `localhost:9000`. It reads Supabase with a `service_role` key, pushes customers/products/invoices/payments as Tally vouchers/masters, and writes `doc.tally` back onto each record. The two apps communicate only through that field.

## Repo-wide conventions

* **Style**: double quotes, no semicolons, 2-space indent (`.editorconfig`), LF endings (`.gitattributes`). Run `npm run lint` (oxlint, per-app `.oxlintrc.json`) before committing.
* **Naming**: components `PascalCase.jsx`; hooks `useThing.js` in `src/hooks/`; pure helpers in `src/lib/`; persistence in `src/data/{store,domain,seed}/` and outbound services in `src/services/` (Admin); static content in `src/constants/` (Web).
* **Imports**: relative paths are the norm; `@/` → `src/` is configured in both front-ends (`vite.config.js` + `jsconfig.json`) for new code. Avoid barrel `index.js` files (they hurt Vite tree-shaking).
* **Never commit** build archives (`*.zip`), screenshots, or `.env*` (except `*.example`). The root `.gitignore` covers the three JS projects; `Ortex.Mobile/` additionally keeps the React Native template's own `.gitignore`, because the root one knows nothing about Gradle/Xcode/CocoaPods output.
* Keep this file and the root `README.md` in sync when adding modules, routes, dependencies or commands.

### Architecture
* **Routing**: Defined in `src/App.jsx` (pages lazy-loaded). Route SEO metadata is mirrored in `scripts/routes-meta.mjs`; `check-meta.mjs` fails the build if the two drift, and `prerender.mjs` writes real `<title>`/OG tags per route.
* **SEO**: Every page calls `useDocumentMetadata` at the top.
* **Layout**: `components/layout/` (Navbar, Footer, ScrollToTop); shared blocks in `components/ui/` (`PageHero`, `PageCTA`, `Section` = Framer Motion primitives, `Icons.jsx` = Iconsax adapter, the only icon library; import icons from there, not from a package); Home-only sections in `components/home/`.
* **Data**: No server of its own. `lib/supabaseClient.js` reads the live catalogue/work photos and inserts leads; the quote wizard and contact form queue to `localStorage` when offline (`lib/leads.js`). Live Orty (`components/ui/LiveOrty.jsx`, lazy) uses `@google/genai` with a token minted by the `orty-live-token` edge function.
* **Live Orty / Anu** (`components/ui/live-orty/`): one bottom-right widget that morphs (shared `layoutId`) between `Launcher`, `CallPanel` (live / error / summary) and `MiniCall`; `Orb` is a canvas fed by `readLevel()`. Her general knowledge is `prompt.js`, hand-copied from `FAQ.jsx`, `constants/site.js`, `products.js` and `About.jsx`, so **a fact changed there must be changed in the prompt too**. The **products** she talks about are live: `catalogue.js` reads `products_public` / `categories_public` (migration 0020, so never price/cost/HSN/GST) at the start of every call, appends a compact index to the system instruction (~420 tokens for 12 products, capped at 120 products) and answers the `lookup_product` tool with one product's real material, MOQ, dispatch days, its category siblings and cross-category add-ons (`AFFINITY`). **A product added or edited in the console is therefore described on the next call, with no deploy.** Matching requires a hit on name/category/material: a description-only hit once returned an acrylic keychain for "wedding invitation cards". No match is not a refusal, it is a **custom run**: Anu captures it with `custom: true`, which `leads.js` folds into the item notes as "Custom item (not in catalogue)". If the read fails she falls back to the prompt's general range. **The page, not the model, owns the rules of a call**: every `capture_lead` goes through `validateLead` (`leads.js`: real name, 10-digit mobile, a numeric quantity per item incl. lakh/crore, timeline, city) and is answered with `missing` + a `next` instruction; `end_call` with reason `completed` is refused once while the five details are missing or unconfirmed (`MAX_END_REFUSALS`). The panel's "Your details" checklist renders that same validated state. **Recording**: `recording.js` mixes both voices into one Opus file and, only when the call produced a lead, uploads it to the private `voice-recordings` bucket (Admin migration 0025: anon insert-only under `calls/<year>/<uuid>.<ext>`, staff read on `voice-leads`); every lead row carries `doc.call = { id, recording, confirmed, complete }`. **Recording is not disclosed to the caller** (the notice was removed on the owner's instruction on 2026-09-12); the privacy policy still does not mention it either, which is a DPDP-notice risk worth raising before launch. Autoplay: audio contexts are created before the first `await`; a timer-opened call shows "Turn on sound". Dev-only `window.__anu` reports output state and chunk counts.
* **Deploy**: `vercel.json` (Vercel) and `public/.htaccess` + `docs/DEPLOY_HOSTINGER.md` (Apache static hosting).

### Architecture
* **Environments**: **two Supabase projects, three environments**, development (`npm run dev`) and staging share one non-production database; production has its own. Vite loads `.env` in every mode and `.env.<mode>` overrides it, so every build runs `scripts/check-env.mjs` first: it refuses a production build that would fall back to the shared dev/staging database, and deliberately allows dev and staging to match. See `Ortex.Admin/docs/ENVIRONMENTS.md`.
* **Database & Auth**: Supabase. **Deleting a quotation is admin-only in the DATABASE** (`0022_admin_only_quotation_delete.sql`): 0007's `staff_quotations` `for all` policy is split into read/insert/update on `has_module_access('quotations')` plus a separate `admin_quotations_delete` on `is_admin()`. The role check the phone and the console do is now the second line of defence, not the only one. A quotation carries an allocated number from `sequences`, and deleting one leaves a hole in the series. `src/data/store/repository.js` resolves to `apiStore` when env vars are present, else `localStore` (offline fallback). Auth is password + emailed OTP (`src/lib/auth.js`), invite-only signups, RLS in migrations.
  * **Audit trail** (`0023_audit_trail.sql`): `created_by` / `updated_by` on every human-edited collection, stamped by a `stamp_actor` trigger from `auth.uid()` — never by the client, so a forged doc field cannot claim authorship and neither front-end had to change to get correct attribution. `audit_log` is an append-only row per insert/update/delete carrying the actor, the moment and a per-key `{from, to}` diff of the doc (values over 500 chars replaced by a marker); it is written by a SECURITY DEFINER trigger and has **no** insert/update/delete policy, so staff read history and nobody rewrites it. `staff_directory` is the allow-list view (id, name, avatar_url, role — never email, modules or active) that lets a non-admin resolve an actor uuid to a colleague, since `profiles` is owner-or-admin readable. **Not retroactive**: every pre-existing row has `created_by = NULL` and no history, which the UI must render as "Not recorded" rather than a blank name; a NULL actor *inside* a log entry means the service role (edge function, cron, Tally connector) and reads as "Automation". Surfaced by `repo.history()` / `repo.staffDirectory()` → `hooks/useRecordHistory.js` → `components/ui/RecordActivity.jsx` (pass `bare` inside a Drawer or a section that draws its own heading) on the quotation and invoice editors, product detail, enquiry detail, the voice call drawer and customer detail. Mirrored on the phone: `data/repo.ts`, `hooks/useRecordHistory.ts`, `ui/RecordActivityPanel.tsx`.
  * **Lead advisories**: `src/lib/advisories.js` (pure: `enquiryAdvisories`, `voiceCallAdvisories`) returns the ordered list of sentences a person needs before ringing — support outranks everything, then no name, urgent, an unreal quantity, an item with no quantity, no delivery city, a repeat caller, already quoted, an enquiry left new for 2+ days, a failed artwork upload, a submitted rate that no longer matches the catalogue. Ported from the field-sales app (`Ortex.Mobile/src/features/leads/`) and now the single source of that wording for BOTH clients — the console's Voice drawer used to hand-write four of these inline. Rendered by `components/ui/Advisories.jsx` on `EnquiryDetail` (above the tiles) and `voice-leads/CallDrawer`. A gap is stated as the question to ask ("Delivery city not captured. Ask for it before quoting freight"), never left blank.
* **Source layout**: `src/pages/` one page per business module plus the hub pages (`Crm`, `Catalog`, `Billing`, `Insights`) and `Login`; `src/components/{layout,ui,editors,documents}/`, `layout/` AdminLayout (sidebar shell, Ctrl/⌘K `CommandPalette`, right-side `NotificationsDrawer`) + PageHeader, `ui/` (`Ui.jsx` kit, `Icons.jsx` Iconsax adapter, `Chart`, `SectionCard`, `PasswordCard`), `editors/` (CustomerFields, ShipToFields, LineItemsEditor, ImageField, ProductImport, TallyInvoiceImport), `documents/` (DocumentView, ReceiptView); `src/hooks/` (`useCollection.js`, `useProfile.js`); `src/lib/` pure helpers (`pricing.js` GST engine, `analytics/`, `format.js`, `id.js`, `periods.js`, `roles.js`); `src/data/{store,domain,seed}/`, `store/` repository facade + apiStore/localStore/supabaseClient/sync, `domain/` schema, domain rules, settings defaults, module registry, `seed/` demo data; `src/services/` outbound integrations (notify, users, integrations).
* **Edge functions**: `supabase/functions/<name>/index.ts`, each deployable alone. Shared code lives in `supabase/functions/_shared/`: `http.ts` (CORS + `json()`), `auth.ts` (`requireStaff(req)` staff gate), `gemini.ts` (`generateContent`, `extractText`, `logAiUsage`). Import from there instead of redefining. Type-check with `npm run check:functions` (fetches Deno 2 via npx; CI runs it on every push).
* **Key Features**:
  * **Design language**: Metronic 9 Demo 1 (Tailwind/React): white canvas, zinc neutrals, blue-500 primary, 280px sidebar + 70px header with breadcrumb, 12px cards with `CardHeader`/`CardFooter`, buttons on the 3-size squircle scale (see **Design system** below), row-ruled tables via the `mt-head`/`mt-body` classes in `index.css` (horizontal rules only. No vertical column dividers, no outer border). Surfaces are **flat**: every `--shadow-*` token in `index.css` is `none` except the two overlay tokens, which keep a 1px ring so floating UI still has an edge. Don't reintroduce a drop shadow on a component. Tokens live in `src/index.css`; the kit in `components/ui/Ui.jsx`.
  * **Full-Page Editors**: Quotation and Invoice creators use clean full-page dashboards rather than modal views, built on `components/editors/DocumentEditorShell.jsx` (Keystone record-page pattern: back circle + number title + status label, money tiles, sectioned cards, sticky footer). Both editors use `CustomerPicker` (searchable combobox, "create new" first) and `LivePreview` (the real `DocumentSheet` scaled beside the form); layout is a 2/3 (Details & Line Items) and 1/3 (Settings & Notes) split, with the Line Items grid occupying a full-width section.
  * **Spacious Line Items Editor**: `LineItemsEditor` uses a strict `table-fixed` layout with a `min-w-[1024px]` viewport, aligning headers and input cells with matched width classes (`w-24`, `w-20`, etc.).
  * **Hub pages** (tabbed workspaces, pattern in `src/pages/Crm.jsx`): `/crm?tab=leads|enquiries|voice` (Leads, Enquiries, VoiceLeads), `/catalog?tab=products|categories|work`, `/billing?tab=invoices|payments`, `/insights?tab=growth|events` (Growth, Automation). Each embedded page accepts `embedded` and swaps its `PageHeader` for `ActionBar`; a hub is guarded by `HubGuard` (any of its module keys) and each tab by its original module key, so per-user permissions are unchanged. The old single-page routes redirect to the matching tab and preserve router state (`openId`, `openLeadId`, `fromCustomer`, `fromEnquiry`). Enquiries and Voice calls read the same `enquiries` collection; Pipeline is `leads`.
  * **Design system** (Keystone port): tokens live in `src/index.css` as a Tailwind v4 `@theme` over HSL vars, flat shadowless surfaces, 1px hairlines, squircle corners (`rounded-card` 20px, applied with the `squircle` utility on `Card`; `rounded-xl` 20px modals), one indigo brand hue used mostly as tints. **Buttons come in exactly three sizes**, `sm` 30px/12px-500/r12, `md` 40px/14px-600/r16 (default), `lg` 50px/16px-600/r20. Set by `size` on `Button`; add `icon` for a square icon-only button, and never override height, text, padding or radius from a page. Padding is derived, never hand-picked: vertical = (height − line-height) / 2, horizontal = exactly 2× that (7/14, 10/20, 13/26), so the padding alone sums to the stated height. Every button carries `squircle`. `rounded-btn` (6px) is for misc 32px controls (pagination, chips, segmented), not the Button kit. Use semantic utilities only (`bg-card`, `text-muted-foreground`, `text-subtle-foreground`, `text-warning-text`, `bg-success/12`, `shadow-overlay-lg`, `squircle`, `btn-sheen`, `rows-in`); never raw Tailwind hues (`amber-600`) or hex, and no in-page `shadow-*`. Tables: put `mt-head` on the `<thead>` and `mt-body` on the `<tbody>`. Always both, and let `index.css` do the rest (40px header filled with **`--table-head`** (94% lightness. Its own token because the head has to separate from *both* the white card it sits in and the canvas behind it: `--subtle`/`--muted`/`--secondary`/`--well` all collapsed to 98% and vanish into the rows, while `--background` matches the page and makes the card look like it starts at row one), 14px/400 sentence-case labels, 1px row rules with none on the last row, `hover:bg-subtle`). Those rules are **unlayered** CSS, so they beat Tailwind utilities: a `px-4 py-3` or `font-semibold` on a `<th>` is dead markup, not an override. Only the editor grid (`LineItemsEditor`), the two modal preview tables and the printed `DocumentSheet` opt out. Kit: `components/ui/Ui.jsx` (Button/Card/Badge/StatCard/Field/Input/Modal/Drawer/Chip/Tabs/Banner/CloseButton).
  * **Public catalogue boundary** (migration 0020): the marketing site reads `products_public` / `categories_public`, **never** the tables. Those views rebuild the doc key by key as an allow-list, so price, cost, HSN and GST never leave the console. A new product field is invisible to the site until it is named in the view. Visibility is `doc.showOnWebsite` (absent = visible), separate from `status` so a product can be sellable in the console yet unlisted publicly. The anon policies on `products`/`categories` are dropped. Adding a website-facing field means editing the view, not just the doc.
  * **Bulk product import** (`components/editors/ProductImport.jsx`): downloads an .xlsx template (Products sheet + "How to fill" sheet) or CSV, accepts either back, and carries a "Copy AI prompt" button that puts a column-exact prompt on the clipboard so ChatGPT can produce a matching sheet. Two photo routes: the `imageUrls` column (links, stored as-is) and **pictures pasted into the sheet**, SheetJS ignores drawings, so `lib/xlsxImages.js` unzips the .xlsx itself and walks sheet → `_rels` → `drawing1.xml` anchors → `_rels` → `xl/media/*`, keying each picture by its anchor's `<xdr:from><xdr:row>` (0-based, header included; data row *n* is sheet row *n+1*). Those bytes upload to the `product-images` bucket at **import** time, never at preview, so a cancelled preview leaves no orphans. `xlsx` and `fflate` are dynamically imported so they stay out of the main bundle.
  * **Form controls**: one `CONTROL` class string in `Ui.jsx` backs `Input`, `Textarea` and `Select`, 45px tall, 16px squircle corners. `Select` is **not** a native `<select>`: it is a portal-rendered listbox that still takes `<option>` children and a `value`/`onChange` pair (the handler gets an event-shaped `{ target: { value } }`), so call sites are unchanged. It portals rather than absolutely positions because several selects sit inside scroll containers that would clip the popup.
  * **App icon / home screen**: `public/icons/app-icon-1000.png` is the master (Ortex "O" on #2F50E4, already padded for maskable). `npm run icons` regenerates 512/192/180/32 from it via `scripts/icons.mjs` (pure-JS box filter, pngjs). Never hand-edit the generated files. `public/manifest.webmanifest` + the head tags in `index.html` wire them up for Add to Home Screen. There is **no service worker yet**, so this is icon + standalone display only, not a fully installable offline PWA (that is phase 1 of the "Ortex Go" plan).
  * **List-page toolbars**: one row above the table: the `ChipGroup` filter rail on the **left**, and a right-pinned (`ml-auto`) cluster of `SearchInput` then the secondary actions, spaced `gap-[10px]`. Toolbar controls match the 45px search pill rather than the three standard button sizes: `ToolbarButton` (labelled, Payout, Import, IndiaMART CSV) and `ExportButton` (45×45, icon-only, white fill that stays white on hover, 20px bold download icon going muted→primary) both take `h-[45px] rounded-[18px] squircle` from one `TOOLBAR_SHAPE` constant in `Ui.jsx`. Use those two components; never override a height or radius from a page. The page title and the primary create button live in the table's own `CardHeader` (`title` + `action`). `Enquiries` is the reference implementation; `InvoiceFilters` and `CallFilters` take the cluster's buttons as an `actions` prop. `SearchInput` hides the browser's native clear cross and draws its own 18px Iconsax bulk cross, muted by default and `text-danger-hover` (#E82646) on hover.
  * **Users** (`/users`, module key `users`, admin only: labelled "Users" in the sidebar): accounts, roles and per-user module access. Creating a login is the `admin-create-user` function; everything afterwards is `admin-manage-user` (`set-active` / `reset-password` / `delete`), reached through `setUserActive`/`resetUserPassword`/`deleteUser` in `src/services/users.js` and the row kebab in `src/pages/users/RowActions.jsx`. Deactivating writes `profiles.active = false` **and** bans the auth user, so RLS hides everything and sign-in (password or OTP) is refused. Deleting removes the auth user; `profiles.id` cascades. The function refuses to disable or delete the caller's own account. That rule lives server-side, not just in the UI.

The header renders Iconsax **Linear** icons (the rest of the app is `Bulk`), pass `variant="Linear"` on those icons.

Providers: `simulate` (Gemini role-play, default) and `vapi` (real calls). Settings block `settings.telecaller` is mirrored by `DEFAULT_TELECALLER` in the shared module. ## Ortex.Mobile (Field-Sales App)

### Commands
```bash
# From Ortex.Mobile/ (needs .env: copy .env.example, same Supabase project as Admin)
npm start          # Metro
npm run android    # native build + install (bare RN CLI, not Expo Go)
npm run ios        # needs a Mac + pod install; never yet compiled, developed on Windows
npm run lint       # oxlint
npm run typecheck  # tsc --noEmit
npm test           # node --test: GST parity with Ortex.Admin, formatters, voice folding
npm run format     # prettier
npm run icons      # regenerate launcher icons from assets/app-icon-1000.png
```

### Architecture
* **Launcher icon**: `assets/app-icon-1000.png` is the master (Ortex "O" on #2F50E4). `npm run icons` (`scripts/icons.mjs`, pure-JS box filter over pngjs) writes every Android `mipmap-*/ic_launcher.png` + `ic_launcher_round.png` and the whole iOS `AppIcon.appiconset` including its `Contents.json`. **Never hand-edit those, they are generated**. Two platform rules the script handles and that bite silently otherwise: iOS icons must carry no alpha channel (the App Store rejects a 1024px marketing icon that has one), so they are flattened onto the brand blue and written as truecolour; and `ic_launcher_round` must be a genuinely circular asset, not a square one the launcher masks. The same master also backs the Admin's home-screen icon (`Ortex.Admin/public/icons/`).
* **Scope**: four tabs: **Quotes** (the point of the app), **Leads** (a `SegmentedControl` over Enquiries and folded Voice calls), **Products**, **Contacts**. Invoices, payments, settings and users stay in the console.

  **Leads** rows open a page, not a sheet: `EnquiryDetailScreen` (`EnquiryDetail`) and `VoiceCallDetailScreen` (`VoiceCallDetail`), sharing `features/leads/leadUi.tsx` (`Advisory`, `StatusStepper` ported from the console's `EnquiryStatusStepper`, `QuickAction`, `Fact`, `ItemRow`). Both are built for the next phone call rather than for the record: **advisories first, in prose**, support/complaint (outranks everything), no name, urgent, an unreal quantity, an item with no quantity, a repeat caller, already quoted, an enquiry left new for 2+ days, then contact circles, then WHAT THEY ASKED FOR. An enquiry from the website's quote calculator carries a whole order as JSON in `notes`; `domain/quoteRfq.ts` parses it, prices it **from our own catalogue and never from the payload** (an anonymous insert could forge a rate), says how many lines it could actually price, and flags rates that no longer match. A voice call shows the newest capture as the order plus **"What Anu heard"**. Every capture, newest first, with a FINAL marker and each capture's own items, so a product added or dropped mid-call is visible. A status change on a call writes to **every folded row**. Gaps are stated as the question to ask ("Not captured. Ask before quoting freight"), never left blank.

  **Products** lists only what is sellable. The phone filters to `status === "active"` (absent = active) rather than showing a status filter or badge, so status stays a console decision even though the phone can now set it. A row is a 56px photo, the name, and `category · MOQ`; tapping it pushes `ProductDetailScreen` (route `ProductDetail`), a catalogue page rather than a form: a parallaxing full-bleed gallery (paging, dots and an `n/m` counter for several photos, tap for a black full-screen viewer) under a bar whose buttons are surface-at-90% circles that fade as the bar fills, a two-up fact grid (long-press an SKU or HSN to copy), a read-more description, and a footer pairing the price (ex- and incl-GST) with "Add to quote". Global search still sends a product straight to the quotation editor, deliberately. **Writing**: the FAB and the detail page's edit button open `ProductEditorScreen` (route `ProductEditor`, optional `id`), photos (picked through the native square cropper), details, pricing and website visibility, but **no status control**: a product added from the field is active, and draft/archived stay the console's call, so an edited product simply carries its existing `status` through the payload untouched, saved through `repo.create`/`repo.update` into the same `products` row the console reads, so an edit here is an edit there. `newProduct()` in `domain/schema.ts` mirrors the console's factory, and the update path is the console's own top-level merge, so fields the phone does not show survive. Photos upload to the shared `product-images` bucket as they are picked (`lib/productImages.ts`, base64 → bytes like `avatarUpload.ts`, because an RN `Blob` uploads 0 bytes silently). No new migration was needed for any of it: `staff_products` (0007) is `for all` under `has_module_access('products')` and the bucket's policies (0010) admit any active staff, so the database enforces the same permission the tab does. **Check the bucket actually exists** in the target project before blaming the client, production had 0010 recorded in `schema_migrations` while the bucket itself had been deleted from the dashboard (re-applied 2026-09-06), which `supabase db push` would have skipped; every upload failed with "Bucket not found". Tabs are gated by the console's own `canAccess`, so a Sales Executive's default grants (`voice-leads, enquiries, customers, quotations`) simply do not render a Products tab.
* **`src/domain/` is a MIRROR: edit both sides.** Line-for-line ports: `pricing.ts` ← `Admin/src/lib/pricing.js`, `format.ts` ← `lib/format.js`, `id.ts` ← `lib/id.js`, `gstStates.ts` ← `lib/gstStates.js`, `schema.ts` ← `data/domain/schema.js`, `settings.ts` ← `settingsDefaults.js`, `quotations.ts` ← `data/domain/domain.js` (quotation slice), `modules.ts` ← `data/domain/modules.js`, `voice.ts` ← `pages/voice-leads/helpers.js`, `quoteRfq.ts` ← `lib/quoteRfq.js`, `data/repo.ts` ← `data/store/apiStore.js`. `test/pricing.test.mjs` imports **both** implementations and asserts identical totals; `test/loadTs.mjs` is the shim that lets Node load a TS file with an `@/` alias alongside a Vite-style extensionless-import file.
* **Two deliberate divergences from the console**: (1) `format.ts` hand-rolls Indian lakh/crore grouping instead of `toLocaleString("en-IN")`, Hermes' `Intl` varies by build and degrades *silently* to Western grouping on a printed quotation; (2) PDFs are `documents/quotationHtml.ts` (the `DocumentSheet.jsx` layout as an A4 HTML string) rendered by `expo-print` and shared with `expo-sharing`, not `html2pdf.js`/`html2canvas`, which are browser-DOM only.
* **Data**: every table is `{ id, doc jsonb, created_at, updated_at }`; `data/repo.ts` flattens rows, pages past PostgREST's 1000-row cap and shares one realtime channel with a **listener set per table** (`repo.subscribe(cb, table)`; omit the table only for a page that shows several collections). `data/collectionStore.ts` holds **one in-memory copy of each collection** shared by every `useCollection` (a `useSyncExternalStore` view over it): a table is fetched once however many screens read it, an in-flight fetch is shared, a realtime event refetches that table once (coalesced over 250ms), and returning to the foreground re-joins the channel and refreshes anything older than 15s. `repo.fetch()` mirrors each collection into AsyncStorage and serves the cache when the fetch throws, and says so: the snapshot carries `fromCache` / `cachedAt` / `error` / `refreshing`, which the four tab lists draw as `ui/DataNotice` ("Showing saved copy from 2 h ago, tap to retry") plus `ui/ListRefreshControl` pull-to-refresh, with an error `EmptyState` when there is nothing cached. `repo.get()` falls back to the cached collection too, so a detail page opened offline still opens. **Writes are never queued offline**. Company settings are read through the **`settings_staff` view** (`0024_staff_settings_view.sql`): the `settings` table is admin-only and holds integration keys, so a Sales Executive reading it got an empty result that used to be merged over the demo defaults and cached (placeholder GSTIN on their PDFs, Delhi as the home state); an empty read is now an error, `useSettings` exposes it, and the quotation editor shows a warning before anything is typed. The profile is cached per user (`@ortex/profile`) so a cold start with no signal still draws the right tabs; a first-ever launch offline, or a profile that grants no module, renders `features/auth/AccountUnavailableView` instead of crashing the tab navigator. A quotation number comes from the atomic `next_sequence` RPC, so two offline phones would both claim the next one; what is kept locally is the half-finished draft (`features/quotations/useQuotationDraft.ts`).
* **Auth**: password → emailed OTP, ported from `Admin/src/lib/auth.js` including the ephemeral-client trick, plus an optional `expo-local-authentication` app-lock with a 60s grace (`features/auth/useAppLock.ts`). No sign-up path; accounts come from the console's `admin-create-user`.
* **Profile**: three screens, not one. `ProfileScreen` (route `Profile`) is the **hub**, photo, fingerprint lock, theme, legal, sign out: what is true of this handset. `AccountDetailsScreen` (`AccountDetails`) is the **record**, name and phone are editable through one bottom sheet, sign-in email and role are read-only because migration 0003's `profiles_protect` trigger forces them back for a non-admin caller, and the module list is read-only for the same reason. `ChangePasswordScreen` (`ChangePassword`) ports `Admin/src/components/ui/PasswordCard.jsx`: the current password is re-checked on an **ephemeral client** before `updateUser({ password })`, so an unattended unlocked phone cannot be used to lock its owner out. `phone` needs **`0021_profile_phone.sql`** pushed; like `avatar_url` it is outside the protected column list, so the existing `profiles_self_update` policy covers it. `LegalScreen` (`Legal`, param `doc: "privacy" | "terms"`) renders `features/profile/legal.ts`. A **verbatim mirror of `Ortex.Web/src/pages/Privacy.jsx` and `Terms.jsx`**, edit both sides; it is local rather than a WebView so the terms open with no signal.
* **Quotation editor** (`features/quotations/QuotationEditorScreen.tsx`): the console's 2/3-1/3 dashboard becomes **three answers and a receipt**, WHO (the picker, then a card head naming who this is for, face, name, "Change", with the seven fields inline beneath it; the place-of-supply picker is tinted as a warning while unset, because unset silently taxes the document as local), WHAT (line rows, one unmissable add action), HOW MUCH (a receipt whose first line states the tax treatment **in words**, so IGST is never first noticed at the bottom of a sent PDF). The customer fields stay **inline on the page**, under a card head that names who the quotation is for: they belong to the document being written, and checking a GSTIN mid-quote should not be a modal round trip. The sticky footer carries the live grand total, and swaps it for the blocking reason ("Choose a customer" / "Add at least one item") while the quotation cannot be saved, so validation arrives before the button is pressed rather than as a toast after. The `min-w-[1024px]` line-items grid is still `LineItemSheet`. One line at a time, product picker plus number fields (quantity has −/+ steppers), replicating `pickProduct` (fills description/HSN/rate/GST, raises quantity to MOQ). `CustomerPickerSheet` mirrors the console's combobox with "New customer" pinned first; `StatePickerSheet` makes the GST state code a picker, because a typo there is a wrong tax split.
* **Keyboard**: `hooks/useKeyboardAwareScroll.ts` is the one answer to "the field is behind the keyboard", worn by `ui/KeyboardAwareScrollView` (the quotation editor), `AppScreen`'s non-list branch (every form screen) and `ui/Sheet` (which lifts by the keyboard height). Neither of the usual answers works alone: `android:windowSoftInputMode="adjustResize"` shrinks the activity but never moves the focused field **and does not reach inside a `Modal`**, which is what every bottom sheet is; `KeyboardAvoidingView` pads the whole view, so on Android with `behavior={undefined}`, what this app used to pass. It did nothing at all. The hook asks RN for the focused input, measures it against the scroll view and scrolls by the overlap, and hands back the keyboard height for bottom padding (without which the last field is unreachable on iOS).
* **Contacts**: a `customers` doc holds exactly **one** contact and the console matches on email-then-phone, so one company legitimately has several rows. The tab is a **Samsung Contacts port**: A–Z sections with sticky letter headers, a draggable alphabet rail (`ContactIndexBar`, PanResponder + haptic detents), a pinned ★ Favourites group, search, swipe-a-row-right-to-call / left-to-WhatsApp (`ContactRow`), long-press multi-select with a bottom Favourite/Share bar, and the contact count at the end of the list. "Sort by company" in the overflow menu re-letters the whole list and is the old group-by-company view. `CustomerDetailScreen` is One UI's contact card, 96px avatar, name, round Call/Message/Email/Quote circles, grouped info cards on the recessed plane, then the quotation/enquiry history. Favourites are **local to the handset** (`lib/favourites.ts`, AsyncStorage + a module store), not a `customers` field: it is "who I ring", and the console has no such column. `lib/contact.ts` carries `tel:` / `wa.me` / `mailto:` with the console's `whatsappNumber` normalisation. **Creating a contact** is the FAB (and both empty states) → `ContactEditorScreen` (route `ContactEditor`, optional `prefill`), the first place in the app that writes a `customers` row directly rather than as a side effect of quoting. Its rules are pure and tested (`features/contacts/validateContact.ts`, `test/contact.test.mjs`): name-or-company (`upsertCustomer` drops a record with neither), phone-or-email (nothing can be matched by `sameCustomer` without one), a 15-character GSTIN whose leading state digits must agree with the place of supply. A mismatch is a wrong CGST/IGST split, and a pre-insert duplicate check on the same email-then-phone rule. `nationalDigits` strips +91/trunk-0 before storing, so a number typed any way still matches the 10-digit shape quotation snapshots carry.
* **Design system**: One UI, ported from the `C:\Dev\Mobile App` project per its `src/ui/README.md`. **The page gutter is 20** (`theme/tokens.ts`, raised from Capnix's 16 on 2026-09-06) and nothing hardcodes an inset, so pages, panels, rows and fields all move together. **Sections are Capnix panels, not cards, on EVERY screen**: full-bleed on `surface`, no radius or border, separated by a literal 2dp band of `colors.border`, and each panel draws its OWN bottom band (a screen that inserts separators between children breaks the moment one is conditional). `ui/Panel.tsx` is the primitive (`title` / `meta` / `action` / `padded`); `ui/Section.tsx` is that same panel plus the grouped-row rhythm. **Two caller rules**: a page adds no horizontal padding of its own. A panel reaches both edges and pads itself by `gutter`, and loose content between panels (a hint, a submit button, an advisory) carries the gutter itself. A nested tile, like the stat squares on a contact, stays rounded: inside a panel is the one place a card shape still belongs. Converted screens: quotation editor and detail, contact editor and detail, enquiry and voice-call detail, product editor and detail, profile, account details, change password. `theme/theme.ts` keeps that palette unchanged. It is the same Metronic ramp `Admin/src/index.css` uses, and adds `theme.tones`, mapping the console's status `tone` names onto it. Type is **Zalando Sans**; every component sets `fontFamily` from `theme/typography.ts`, never `fontWeight` (custom fonts do not synthesise weights on Android). Conventions: slim toolbar above a 30px title, **bottom sheets not dialogs** for short choice lists, hairline dividers inset 16px, a 60px FAB clear of the tab bar, 28px squircle cards / 16px buttons / 12px fields. The source kit's `GlassTabBar` is **not** ported. It is an iOS-26 idiom whose Android blur needs a config plugin that never runs in a bare project; `navigation/OneUiTabBar.tsx` replaces it.
* **Bare-workflow gotchas**: `app.json` config plugins **do not run**. Native wiring is by hand, `AndroidManifest.xml` (`USE_BIOMETRIC`, `VIBRATE`, `READ_MEDIA_IMAGES` + `READ_EXTERNAL_STORAGE` capped at SDK 32 for expo-image-picker, and an Android 11+ `<queries>` block without which `Linking` cannot see the phone/mail/WhatsApp apps) and `Info.plist` (`NSFaceIDUsageDescription`, `NSPhotoLibraryUsageDescription`, `LSApplicationQueriesSchemes`). Both photo pickers also call `requestMediaLibraryPermissionsAsync()` themselves: a denied library makes `launchImageLibraryAsync` return a plain `canceled`, so without the check a refused permission looks exactly like the person changing their mind. The `@/` alias comes from `babel-plugin-module-resolver` in `babel.config.js`, **not** tsconfig `paths`. That is resolved by Expo's Metro integration, and bundles here are built by the RN CLI's Metro. Env is `react-native-dotenv` (`SUPABASE_URL`, `SUPABASE_ANON_KEY`).
* **Lint**: `react/refs` and `react/set-state-in-effect` are off in `.oxlintrc.json`. They fire only on correct RN idioms (`useRef(new Animated.Value(…)).current`, async loads) and buried ~40 false positives.
