# Ortex.Admin (business console)

Repo-wide rules, environments, roles and cross-app mirrors are in the root `CLAUDE.md`. This project **owns the database** for all clients: `supabase/migrations`, `supabase/functions`, `supabase/maintenance` (manual SQL, never run by `db push`).

```bash
npm run dev             # Vite on :5180; no Supabase env -> localStore demo mode
npm run dev:staging
npm run build           # check-env -> production build
npm run build:staging
npm run check:env
npm run provision -- <ref>  # push migrations + deploy every function to a project
npm run check:functions     # Deno 2 type-check of every edge function (CI runs it)
npm run icons               # regenerate icons from public/icons/app-icon-1000.png
npm run lint                # oxlint, then scripts/ui-guard.mjs (em dashes, button sizes, shadows, raw hex)
npm test                    # vitest (pure lib tests)
npm run test:db             # every migration into a throwaway PGlite + the attendance/leave/payroll flow as real users (supabase/qa)
```

## Architecture

* **Source layout**: `src/pages/` one page per module, plus hub pages; `src/components/{layout,ui,editors,documents,anu}/`; `src/hooks/`; `src/lib/` pure helpers (`pricing.js` GST engine, `analytics/`, `format.js`, `roles.js`, ...); `src/data/store/` (repository facade, `apiStore`, `localStore`, supabase client, sync), `src/data/domain/` (schema, rules, settings defaults, module registry, `whatsNew.js`), `src/data/seed/`; `src/services/` outbound integrations.
* **Data**: every table is `{ id, doc jsonb, created_at, updated_at }`. `data/store/repository.js` uses `apiStore` when Supabase env vars exist, else `localStore`. Demo data (`data/seed/seed.js`) and "Delete ALL data" are for `localStore` only: Settings hides both when `hasSupabase`, and `seedDemo()` / `apiStore.clearAll()` throw on the live database. "Remove demo data" stays, since it deletes only rows tied to the eight sample customers' emails.
* **Auth**: email + password (`lib/auth.js` `signIn`), invite-only; the emailed sign-in code was removed 2026-10-01. Forgot password on `pages/Login.jsx` runs email -> code -> new password on one ephemeral client, so the route guard never sees the recovery session (mirrors `Ortex.Mobile/src/lib/auth.ts`). Hidden in demo mode.
* **Edge functions**: `supabase/functions/<name>/index.ts`, each deployable alone. Shared code in `_shared/`: `http.ts` (CORS + `json()`), `auth.ts` (`requireStaff(req)`), `gemini.ts` (`generateContent`, `extractText`, `logAiUsage`), `images.ts` (`ownStorageUrl`: only fetch our own storage URLs), `guard.ts` (`secretsMatch` constant-time compare, `clientIp`, `withinLimit` rate limit over `rate_limit_hit()`, `callerHasModule`, `clipStrings` for prompt inputs), `fcm.ts` (FCM v1 send, `fcmMessage`, `tokenIsGone`), `pushText.ts` (push words and mutes, tested by `src/lib/pushText.test.js`), `linkedin.ts`, `instagram.ts`, `telecaller.ts`. Import from there, never redefine. Public functions (`orty-live-token`, `automation-engine`) are rate-limited per IP; the old public chat proxy `orty-chat` was deleted (2026-09-26). Functions called by pg_cron or OAuth callbacks are deployed `--no-verify-jwt` and check their own secret. **Deployed with `--no-verify-jwt`: `push-notify`, `indiamart-lead`, `marketing-sync`, `orty-live-token`, `product-copywriter`; every other function in this repo keeps JWT verification on.** Redeploy each group with its own flag (no `config.toml` records it); `npx.cmd supabase functions list` shows `verify_jwt` per function. The project runs exactly the 17 functions in this repo (`attendance-housekeeping` and the retired `social-accounts`, `social-creative`, `social-publish`, `social-researcher` were deleted 2026-10-03).
* **Navigation** (reorganised 1.55.0): a section holds ONE kind of thing. Sales (Leads, Quotations, Billing, Customers), Catalogue, Growth (Call agent, Marketing, Insights, which is no longer hidden behind Ctrl K), People (Attendance, Payroll, My records, which were three sections of one hub), Admin (Users), and the **Control centre** (`/control`, `pages/Settings.jsx`, key `settings`): EVERYTHING the Super Admin configures, in one page with grouped sections. It absorbed `/settings`, `/modules` and the two settings tabs that sat inside the Attendance hub; all three old addresses redirect, as do the moved `?tab=` links (`MOVED_TAB` in `App.jsx`). `pages/Attendance.jsx` takes a `scope` prop ("team", "payroll", "me") and renders one section each.
* **Hub pages** (tabbed, pattern in `pages/Crm.jsx`): `/crm?tab=leads|enquiries|voice`, `/catalog?tab=products|categories|work`, `/billing?tab=invoices|payments`, `/insights?tab=growth|sales|events`, `/attendance?tab=<page>`, `/my-records?tab=<page>` and `/payroll?tab=<page>` (one shell, `pages/Attendance.jsx` with `scope` "team", "me" or "payroll", its pages as `PillTabs`; the URL names only the page, so old `?tab=leave` or `?tab=qr&full=1` links still land, and `MOVED_TAB` in `App.jsx` sends old payroll and settings tabs to their new home; `/payslips` redirects in). Attendance and leave rules live in the Control centre. Insights is not in the sidebar: it opens from the Dashboard header and Ctrl K search (`SEARCH_ONLY` in `AdminLayout.jsx`). Embedded pages take `embedded` and swap `PageHeader` for `ActionBar`. A hub is guarded by `HubGuard` (any of its module keys), each tab by its own key. Old single-page routes redirect to the tab and keep router state (`openId`, `openLeadId`, `fromCustomer`, `fromEnquiry`). Pages open a specific record through `state.openId`.

## Database rules worth knowing

* **Audit trail** (0023): `created_by` / `updated_by` are stamped by the `stamp_actor` trigger from `auth.uid()`, never by the client. `audit_log` is append-only (no write policy) with a per-key `{from, to}` diff. `staff_directory` is the safe view for resolving an actor uuid (no email, modules or active flag). Not retroactive: a NULL `created_by` renders as "Not recorded"; a NULL actor inside a log entry means the service role ("Automation"). UI: `repo.history()` -> `hooks/useRecordHistory.js` -> `components/ui/RecordActivity.jsx`; per person, `repo.actorHistory()` on `/users/:id`. Reading is per module since 0050 (`audit_can_read`), so a timeline shows only records the viewer's modules cover. Wording for an entry is `lib/auditWords.js`.
* **Quotation delete is admin-only in the database** (0022). Numbers come from `sequences` via the atomic `next_sequence` RPC, so a delete leaves a gap.
* **Public catalogue boundary** (0020): the website reads `products_public` / `categories_public`, which rebuild the doc key by key as an allow-list. A new website-facing field means editing the view. Visibility is `doc.showOnWebsite` (absent = visible), separate from `status`.
* **Anu's knowledge base** (0028): `anu_knowledge` is written ONLY by `anu_knowledge_sync` triggers on `products` / `categories` / `work`. The trigger swallows its own errors (it must never block a product save) and bumps `anu_knowledge_version`.
* **Leads become customers** (0029): triggers on `enquiries` and `leads` call `upsert_customer_from()`, matching like `sameCustomer` (email, then national phone digits), filling blanks only, skipping Anu's filler names. An ANONYMOUS enquiry (website, Anu) never fills a matched customer's GSTIN, state code or address (0050): anyone can type a customer's email. The anon enquiry insert is capped at 32 KB with field length limits.
* **Phone push** (`push-notify`, `--no-verify-jwt`, guarded by the `x-push-secret` header): AFTER triggers hand `{ table, id }` to it through pg_net, a no-op until the Vault secrets `push_notify_url` / `push_notify_secret` exist and never failing the write: new enquiries and voice leads (0031, imported rows skipped 0051), leave and correction requests, decisions and cancellations (0038), Team chat (0047), payslips released and claims approved or rejected (0074). Every send goes through `deliver()`: active people only, all their phones in `push_devices`, minus phones whose `muted` (0074, sent by the phone with its token: `enquiries`, `voice`, `chat`, `requests`, `pay`, `all`) covers the category; tokens FCM rejects for good are deleted. Messages are FCM notification messages tagged with the phone's own notification id, carrying `targetScreen` / `targetId` / `kind`; pay alerts never carry an amount. Setup and the owner checklist: `docs/guides/PUSH_SETUP.md`.
* **Settings**: the `settings` table is read by admins and written only by the Super Admin (0050; it holds integration keys); non-admins read the `settings_staff` view (0024). `settings` is `superAdminOnly` in the module registry.
* **Storage buckets**: `product-images`, `avatars` (owner-scoped `<uid>/`), `chat-files` (private, members of the conversation named by the first folder), `voice-recordings` (private, anon insert-only), `social-media`, `app-releases` (public, no list, service-role writes), `attendance-selfies` (private, historical). Public buckets (`product-images`, `avatars`, `social-media`) serve files by URL, but only signed-in users can list them (0050); writing `product-images` needs the products, categories or work module, `social-media` the social module. If uploads fail with "Bucket not found", check the bucket exists: `db push` will not recreate one that was deleted by hand.

## Modules

* **Dashboard** (`pages/Dashboard.jsx` + `pages/dashboard/`, the Figma "Dashboard v2" design): a page for the next hour. A main column for the work ("Needs you today" = `attentionItems` + `approvalItems`: leave, corrections, pay runs, and Call agent hand-offs join the quote-to-cash items; leave is approved in place, everything else opens its page; then Cash flow, Pipeline, Automation health, Payroll or Catalogue) and a 360px rail for live operations (gate QR card, Team today, Receivables, Lead sources, People and access, Recent activity from `audit_log`). Quote-to-cash figures are pure functions in `lib/analytics/today.js` (tested); the other reads are `services/dashboard.js` (`loadOps`, each read independent so a missing migration drops only its card). Every card is gated by the module it reads. Longer-range analysis is Insights -> Sales (`lib/analytics/sales.js`).
* **Enquiry import** (Enquiries -> Import, console 1.47.0; the phone Leads screen has the same import in code, `features/leads/EnquiryImportSheet.tsx`, but it ships only with the next phone release, because `expo-document-picker` needs a new native build): the sales call-log workbook (Date, Name, Mobile No., Status, Mobile No.2, Type of Product, Quantity, Rate, City, company Name, Email id) becomes enquiries through `lib/enquiryImport.js` (tested). A date applies to the rows under it and becomes `created_at`; the Status words map to the six statuses and stay in `notes`; `quantity`, `rate`, `altPhone` and `customer.city` are enquiry fields. Rows carry `doc.imported`, which skips alerts (migration 0051 for push), and a row matching a saved lead or an earlier row (same mobile, else name; same product; same IST day; a sheet with no dates matches on person and product) is left out and listed with what it matched, and a mobile that is already a lead on another product or day starts unticked (`repeats`). `supabase/maintenance/remove-duplicate-enquiries.sql` removes such duplicates and empty enquiries already in the table.
* **Leads and enquiries** (sidebar "Leads", `/crm`; the Figma "V2 · Leads" frames): `enquiries` holds web enquiries AND Anu voice captures. The list (`pages/Enquiries.jsx`, rows built by `pages/leads/model.js`) is one table, newest first, with smart views, phone and location, product and quantity, a derived next step, pagination and keyboard shortcuts; a row opens `/enquiries/:id` (`pages/EnquiryDetail.jsx`), P opens the quick preview (`pages/leads/LeadPreview.jsx`). Every write a lead takes is `pages/leads/actions.jsx`. The next step and its due time are `leadNextStep` in `lib/salesWork.js` (tested): a person's `followUpAt` (Snooze, Set follow-up) wins over the date derived from the status. Console-only doc fields: `followUpAt`, `nextStep`, `statusAt` (dates on the progress track), `activity` (notes, calls, WhatsApp and follow-ups written on the lead page), `tags`. The Voice calls tab (`/crm?tab=voice`) is unchanged; Voice calls folds them per conversation with `voiceCallsFrom` (`pages/voice-leads/helpers.js`). `leads` is the pipeline. `lib/advisories.js` (`enquiryAdvisories`, `voiceCallAdvisories`) is the single source of the pre-call advice for BOTH clients: each gap is phrased as the question to ask. Recordings play in the Voice drawer through 1-hour signed URLs (`services/voiceRecordings.js`); a missing object reads "Recording not available", not an error.
* **Quotations and invoices**: the quotation list, detail and send screens follow the Figma "V2 · Quotations" frames: `pages/quotations/QuotationList.jsx` (smart views, follow-up column, row quick actions), the editor in `pages/Quotations.jsx` (sticky totals rail, `quoteChecks` pre-send checks, save bar), and `pages/quotations/SendScreen.jsx` (full-size A4 plus a WhatsApp / email send panel). Send, remind, extend validity, convert and duplicate are `pages/quotations/actions.js`; a send stamps `sentAt` and appends `sendLog`, a status change stamps `statusAt`. Follow-up rules are `quoteFollowUp` in `lib/salesWork.js` (a sent quote is due three days after sending unless `followUpAt` says otherwise). The invoice editor still uses `components/editors/DocumentEditorShell.jsx` with `CustomerPicker` and `LivePreview` (the real `DocumentSheet`, scaled). Customer checks in `lib/validateCustomer.js`. Printed wording is settings, edited in Control centre -> Documents: `quotation.terms`, and the `documents` block (`invoiceTerms`, `quotationFooter`, `invoiceFooter`, `receiptFooter`), which staff read through `settings_staff` (0071). The tax invoice always prints "Tax Invoice", Reverse charge: No and a For <company> / Authorised signatory block (GST Rule 46). `supabase/maintenance/document-wording.sql` moved saved records off the old default wording. Per-rep quotation defaults in `profiles.quotation_defaults` (0027; `lib/quotationDefaults.js`). Local drafts in `lib/quotationDraft.js`. WhatsApp share: `lib/quotationShare.js` + `components/documents/documentPdf.jsx`. Print is `window.print()`, PDF is `html2pdf.js`, A4 with notes pinned by `mt-auto`. **Every console PDF (quotation, invoice, payslip, receipt) is one A4 portrait sheet built by `buildSheetPdf` in `documentPdf.jsx` with `lib/a4.js`**; `lib/a4Only.test.js` fails if html2pdf.js is used anywhere else or a page size is set locally (QuestPDF was considered and declined, 2026-10-02: it needs a .NET server).
* **Payment screenshot reader** (the Record payment / payout drawer, `pages/invoices/RecordPaymentModal.jsx` + `ScreenshotReader.jsx`): NO language model and no upload. A screenshot from any UPI app (Google Pay, PhonePe, Paytm, BHIM, Amazon Pay, CRED, WhatsApp, MobiKwik, Navi, super.money and the rest) or a bank's NEFT / RTGS / IMPS confirmation is read in the browser by Tesseract.js (LSTM OCR, web worker; worker, core and the 10 MB English model load from jsDelivr once). **Page layout is forced to automatic (`tessedit_pageseg_mode` 3)**: tesseract.js defaults to one uniform block, which throws away an app's big headline amount. Before recognition `evenPolarity` (tested) flips dark mode, inverts coloured bands with white text (a band is a row whose MEDIAN is dark) and stretches every row's background to white, because a grey or coloured band is otherwise dropped as a picture. Every read runs the complete pass: greyscale, Otsu-thresholded, and the headline at 400px and 800px (too large to recognise at full size); `combineReadings` votes field by field, ties to the earlier pass. Whether a leading 3, 7, 2 or 8 is really the ₹ is decided by the glyph's pixels (`looksLikeRupee`, tested on a real Google Pay "₹4,000.00" that Tesseract read as "34,000.00" at 95%): a ₹ has two full-width bars in its upper half, a digit never does. Confidence and box width cannot tell them apart; confidence is the fallback only when the glyph is too small to judge. `lib/paymentReader.js` (tested) parses each app's labels; the amount is the number in the largest font (`pickHeadline`, 1.5x the median line, so a pincode never wins), fixing the ₹ glyph read as R, %, 3 or 7 (`headlineAmount`: broken Indian grouping is certain, otherwise the first glyph's shape decides and the drawer offers the other amount in one click); the app comes from its name on screen, else the sender's UPI handle (`@ybl` PhonePe, `@okicici` Google Pay, ...). Then the reference (a UTR or 12-digit RRN beats an app's order id), the method, short warnings (`serious` for failed or not a payment, shown red), a duplicate in the ledger (same reference = certain; same amount, day and payer = possible), and the open invoice it pays (amount plus payer, or the invoice number in the remark; a tie links nothing). The drawer leads with the amount, marks every filled label with a sparkle, keeps everything editable, never lets an invoice pick overwrite a read amount, and asks before saving a certain duplicate or a serious reading. Verified in Chrome on 19 receipts including a real Google Pay screenshot (scratch harness, not in the repo).
* **Payment direction**: a payment is `type` "inflow" (money received, shown as Received / +) or "payout" (money paid out, Paid out / minus); the person picks it by the button that opens the drawer (Record payment / Record payout) or the phone's Received / Paid out switch. A screenshot is checked against the company's own details by `paymentDirection()` in `lib/paymentReader.js` (tested): the company as payee, or its UPI ID on screen, means money in; the company as payer, or a debited bank line ending in the last 4 digits of `company.bankAccount`, means money out; neither or both says nothing. When it disagrees with the form the drawer says so in red, offers "Record it as a payout" / "money received" in one click (not for a payment pinned to an invoice), and Save asks first. It only works as well as Settings -> Company is filled in: name, UPI ID, bank account, and **Other names and accounts** (`company.paymentAliases`, one per line: an owner's or partner's name, a personal UPI ID, another account, masked numbers like "XXXX 1912" allowed), which also count as the company. That list travels in `settings_staff`, so every staff member can read it.
* **Payments records** (Billing -> Payments, `pages/Payments.jsx`, the drawer above; module `payments`): **the database owns the money rules (migration 0066)**. A payment's amount must be a number above 0 and below 1e10, a payout carries no invoice, an `invoiceId` must exist, numbers are unique (`payments_number_key`; a UTR is NOT unique, since one transfer can pay two invoices, so both clients ask "Record again?"), `created_at` is the server's, and `doc.tally` is written only by an admin's Import from Tally (0070, 0072) or the service role (`tally_mark()`, for the unused connector); everyone else's is stripped. A payment already in Tally can be changed or deleted only by the Super Admin, who must change it in Tally too. An invoice's `amountPaid` / `status` / `paidAt` are recomputed IN SQL on every payment change and every invoice save (settled within ₹0.50), so the browser never writes them on Supabase (`syncInvoicePaid` runs only in localStore demo mode, and `updateInvoice` strips them). An invoice with payments cannot be deleted (cancel it). The shared money maths is `lib/invoiceMoney.js` (tested): `SETTLE_TOLERANCE`, `paidByInvoice` (one Map per payments array), `resolveInvoiceStatus` (from the numbers only), `outstandingBalance` (drafts owe nothing), `paymentsOrStored` (people without `payments` see the stored `amountPaid`), `receiptAllocation` (a receipt shows what was paid up to THAT payment). Dates are stored as noon IST of the chosen day (`paymentDateIso`), as on the phone. A receipt prints "Receipt Voucher" and the GST Rule 50 note only for an unlinked inflow marked `advance`; the internal note never prints. `next_sequence` needs the matching module (payment/invoice/quotation). `getSettings` reads the admin `settings` row, else the `settings_staff` view, else (only for an admin, a fresh project) defaults; anyone else gets an error rather than placeholders on a document. A linked payment's `invoiceNumber` and `customer` are copied from its invoice by the database (so Tally settles the same bill), `doc.account` is the connector's alone, ids cannot change, a synced payment also freezes its customer, number, reference and invoice number, and anon cannot SELECT payments, invoices, customers or quotations. Tally imports are admins only (see Import from Tally below). Edge functions merge doc patches server-side through the service-role `doc_merge()` (0066), never a whole-doc rewrite.
* **Import from Tally** (Billing header, admins only; `pages/billing/TallyImport.jsx` + `lib/tallyImport.js`, tested): **the only way Tally data comes in** (owner's decision 2026-10-03: manual, no connector, API or server access). A person exports XML (Data Interchange) from TallyPrime: the Day Book for Sales, Receipt and Payment vouchers, and List of Accounts for Sundry Debtor ledgers, groups, voucher types and stock items, and uploads any number of files (UTF-16 or UTF-8; Tally's illegal characters and Dr/Cr numbers handled). Rules:
  * **Identity is Tally's GUID** (`doc.tally.guid`): the same GUID with a higher ALTERID updates the row ("Changed in Tally"), otherwise it is skipped; `ortex-` remote ids (made in the console) are skipped. A preview counts New / Changed / Already imported / Made in the console / Link to invoice / Left out / Problems before anything is written.
  * **Kinds**: a custom voucher type follows its VOUCHERTYPE parent, else is read from its entries (a credit to Sales Accounts, goods out with a New Ref, cash or bank debited or credited). Masters learned from an upload (voucher type parents, the group chain, ledger groups, GST duty heads) are remembered in that browser (localStorage `ortex.tallyMasters.<user>`), so a later Day Book alone is read the same way.
  * **Customers** are ledgers whose group chain reaches Sundry Debtors; they fill blanks only on a console customer matched by email, phone, GSTIN, then name. A receipt from a ledger known to be outside Sundry Debtors (capital, loans) is left out ("Not from a customer"), and a payment's party never becomes a customer. **Products** fill blanks only and arrive `draft` + `showOnWebsite: false`, with the GST rate and selling price in force today (never the opening cost).
  * **Tax** comes from the ledger master (GST duty head / Duties & Taxes), never from a sales ledger's name; taxable + tax + round off = grand total. Invoices carry Tally's totals and lines only when the voucher has inventory, so `DocumentView` must still default defensively.
  * **Payments**: the reference is the UTR or cheque number, not Tally's internal key; RTGS, UPI, Card and Cheque map to the console's methods. Receipts link by Agst Ref (a receipt over several bills is split), and store Tally's bill number as `tallyBill`, so a receipt imported before its invoice shows "Link to invoice" when the invoice arrives and is linked on import (0072: an admin may set `invoiceId` on an unlinked imported inflow when nothing else changes). Receipts and payouts are separate number series (`R-` / `P-` on a clash); a number Tally reused in a new financial year becomes `<n>/<FY>`.
  * **Stamp** on every record: `{status:"synced", source:"tally", syncedAt, voucherRef, guid, alterId}`, which the database keeps only for an admin (0070); an imported payment changes only through a re-import with a higher alterId, or the 0072 link. The old `{status, syncedAt, voucherRef}` shape is still accepted; the invoice editor no longer has its own Tally import (Billing -> Import from Tally is the one way in).
  * **Testing**: realistic exports and expected preview counts are kept outside the repo (`Downloads\Tally import test\`, with a README); test on the local demo console, never production, since imported payments are frozen and invoices with payments cannot be deleted.
* **Catalogue**: bulk import in `components/editors/ProductImport.jsx` (xlsx/CSV template, "Copy AI prompt", `imageUrls` column, and pictures pasted INTO the sheet, extracted by `lib/xlsxImages.js` from the drawing anchors and uploaded at import time, never at preview). `xlsx` and `fflate` are dynamically imported. `xlsx` is SheetJS 0.20.3 from `cdn.sheetjs.com` (npm's 0.18.5 has known prototype-pollution and ReDoS bugs, and SheetJS no longer publishes to npm); files over 20 MB are refused before parsing.
* **AI writer and photo studio** (functions shared by both clients): `ai-writer` is the one "Write with AI" backend (`purpose`, `context`, `mode`, `format`; house rules: Indian English, no dashes, never invent prices/dates/GSTINs/specs). It runs on Gemini's free tier, which may train on prompts, so `context` carries only the record being written. `product-image-studio` edits photos on Cloudflare Workers AI (FLUX.2 klein, secrets `CLOUDFLARE_ACCOUNT_ID` + `CLOUDFLARE_API_TOKEN`), always into a NEW object under `product-images/products/ai/`, and both clients show before/after for a person to accept, because a changed logo on a made-to-order product photo is a misrepresentation.
* **Marketing** (`pages/Social.jsx`, route `/social`, module key `social`): a read-only view of the separate Marketing project (`C:CodeMarketing`): posts live, scheduled or approved on Instagram and LinkedIn, DMs, comments and follow-ups. That project runs `npm run sync:ortex`, which pushes to the `marketing-sync` Edge Function (`--no-verify-jwt`, shared secret `x-sync-key` = function secret `MARKETING_SYNC_KEY`); the function upserts `marketing` rows on `ref` (migration 0052; read needs the `social` module, writes are service role only) and stores post images in `social-media/marketing/`. The console never posts. The old publisher (`social` table, `social_connections`) is retired; its data is kept, nothing reads it.
* **AI Telecaller** (`/telecaller`): `telecaller_jobs` + `telecaller_calls`; engine in `_shared/telecaller.ts`; functions `telecaller-dial`, `telecaller-engine` (pg_cron), `telecaller-webhook`. Providers `simulate` (default) and `vapi`. **The planner auto-calls only IndiaMART enquiries or ones a person has starred**: website and Anu enquiries are anonymous, so anyone could type a stranger's number (security audit 2026-09-26). Enquiry text reaches the agent's prompt marked as customer-written data, never instructions. `telecaller-dial` / `telecaller-engine` need the `telecaller` module (admins pass), and only admins may re-dial a finished job. `settings.telecaller` is mirrored by `DEFAULT_TELECALLER` in the shared module: keep them in step. Setup: `docs/guides/TELECALLER_SETUP.md`.
* **Team chat** (`/chat`, module `chat` = always; migrations **0045** and **0046**): WhatsApp-style direct chats, groups and one private **Anu thread** per person. Tables `chat_conversations` / `chat_members` / `chat_messages` are relational (not `{ id, doc }`) and have **SELECT policies only, for members only**: every write is a security-definer RPC (`chat_send` with a client-generated id so a retry is idempotent, `chat_open_direct`, `chat_create_group`, `chat_add_members` / `chat_remove_member` / `chat_rename` for the group owner, `chat_leave` which hands ownership on, `chat_edit` within 15 min, `chat_delete` for everyone, `chat_mark_read`, `chat_set_muted`, `chat_inbox`, `chat_people`). **Admins cannot read other people's chats.** Files go to the private `chat-files` bucket under `<conversation id>/`, read through signed URLs. A message for a team ("tell accounts that ...") waits for a Send / Cancel card before `chat_post_to_team` posts it. Help articles are `HELP` in `components/chat/assistant.js`: **keep them in step with real button labels**.
* **Anu's team bot** (migration **0046**, all SQL, no model): team channels (`chat_conversations.kind = 'team'`: sales, accounts, staff, management, everyone) whose members are synced from `profiles.role` by a trigger, admins in every team; bot posts are `chat_messages.kind = 'bot'` with a NULL sender. `anu_daily_update(team, day)` and `anu_attendance_report(team, day, phase)` build the text from the business, attendance and leave tables (NULL on a holiday or weekly off); `anu_bot_tick()` (pg_cron `anu-bot-tick`, every 5 min) posts each job once a day within two hours of its time from `anu_bot_settings` (Super Admin), logged in `anu_bot_runs`. ## Attendance, leave and payroll

Plans: `docs/pm/ATTENDANCE_LEAVE_PLAN.md`, `docs/pm/PAYROLL_PLAN.md`.

* **Attendance is marked ONLY in the phone app** (no clock-in on the web). Punches go through the security-definer RPC `attendance_punch()`; `attendance_punches` has no write policy.
* **Proof of presence is a rotating QR code** (0043, replacing the selfie + geofence of 0033). `attendance_qr` holds one token per station (a `work_sites` row); the table has no RLS policy, so the token reaches a browser only through `attendance_qr_show()`, never over realtime. The code rotates every `qrRotateSec` (30s), is burned on a successful punch (the next is issued in the same transaction), and is shown to whoever may open the `attendance-qr` module (`attendance_qr_issuer()` = `has_module_access()` since 0055: every Admin by default, managed on the Modules page). Refusals: `wrong_code`, `used_code`, `expired_code`. **Field staff (Sales) punch with no code** and the row is flagged `no_code` for review. A punch is also flagged `own_code` when the scanner opened that code themselves (`attendance_qr.viewers`, 0065: give the gate kiosk its own account) and `other_site` when the station is not in their `attendance_people.site_ids`. Deciding corrections, leave and flagged punches needs `is_admin()` AND the `attendance-team` module (0065), on both clients. There is no offline punch queue (a 30s code cannot be replayed later).
* **Token generation uses `gen_random_uuid()`, never pgcrypto** (0044): these functions pin `search_path = public` and `gen_random_bytes` lives in `extensions`. `services/attendanceQr.js` surfaces the server's own error text as `detail`.
* **One check-in and one check-out a day** (0042; refusal `day_done`); anything else is a correction.
* **Punch window** (0049, tightened by 0056; refusal `outside_hours`): a CHECK-IN is accepted from `checkInFrom` ("08:30") to `closeAt` ("21:00"), IST, both keys in `attendance_settings.doc` (Attendance → Settings, Super Admin). A CHECK-OUT has no window. An in is open only on its own IST day, so an unclosed day resets at midnight (the next punch is a fresh check-in; the unclosed day is an ABSENCE flagged `no_checkout`, fixed by a correction). **There is no auto clock-out**: `autoCloseAfterMin` is gone from the console and unread, midnight is the only thing that closes a day. An early check-in counts FROM the shift start, so nobody banks time at the gate (`countFromFor` feeds the same floor to `workedMs` and `summarizeDay`). `autoPresent` in the same doc lists people who are P on every working day without punching (flag `auto_present`), and `attendance_overtime` (0056) keeps overtime per day, readable by `attendance-register` or payroll (0065; admins only before): past the shift on a working day, every worked minute on a day off. Corrections are capped at 5 a month, and rejected and cancelled ones count too (0065), so nobody can keep a month from locking by re-filing. The phone checks the same rules first (`punchWindowClosed` / `punchWindowLabel` in `features/attendance/progress.ts`, `onDutySince` in `domain/attendance.ts`).
* **Day statuses** (0034): `attendance_days` (P, HD, A, OD, WO, H, MP, L, LOP) is computed, never typed. A day worked on a weekly off (Sunday by default) or a holiday keeps WO / H with its times, hours and the `worked_off_day` flag, never A, HD or MP: the `attendance_days_keep_off_day` trigger (0058) enforces it whatever version of `attendance_recompute_day()` is live. `holidays` (written by the `attendance-holidays` module since 0057: every Admin by default, set on Modules; UI Attendance → Team → Holidays, add/edit/switch off/remove; a change recomputes that day for everyone and is written to `audit_log`, 0065), `regularisations` (corrections, decided by an admin, never on one's own; since 0065 an approved correction REPLACES the punches of the kinds it gives, which are marked rejected "Replaced by correction", and a time in the future is refused), `attendance_months` (the payroll lock; it refuses while the month has flagged punches, pending corrections or pending leave requests, and only the Super Admin unlocks, with a reason kept in `audit_log`, 0065). An unclosed day is A + `no_checkout`; read it with `missedCheckout()`, never by looking for MP (older rows only). A punch, a correction request, a leave apply/decide and an undo take the same per-person advisory lock (0065), so two of them cannot race past a check.
* **Leave balances** (0059): managed by the `leave-balances` module, which starts with the Admin role OFF (`module_controls` row), so only the Super Admin has it until they tick an Admin on Modules. `leave_adjust` (add / remove; "Set balance" in `leave/Balances.jsx` is a computed adjust) and `leave_undo_adjust` (a `reversal` row whose `ref_id` is the undone entry, from the ledger drawer) check it; nobody but the Super Admin changes their own balance.
* **Leave** (0036): `leave_types` (EL, CL, SL, CO, LOP), `leave_ledger` (every balance change is a row), `leave_requests` (applied on either client, decided by an admin, days counted by the server). pg_cron accrues/lapses. 0038 adds comp-off expiry and push to approvers.
* **Selfies are gone entirely** (migrations 0060 and 0062, 2026-09-30). Dropping `selfie_path` broke every punch until 0062: `attendance_punches_lock_guard` is a BEFORE INSERT trigger and still read `new.selfie_path`. **Before dropping a column, search `pg_proc.prosrc` for it.** They stopped being taken in 0043; the column, the screens that drew them and the `attendance-housekeeping` function and cron job are all deleted. Pre-0043 rows keep their coordinates, which nothing checks. The geofence radius controls went with them: a station has a pin on a map to say where it is, not a fence.
* **Excel export** (Attendance → Register): `lib/attendanceExcel.js` builds a styled workbook with ExcelJS (dynamically imported; SheetJS cannot write formats), one sheet per month with a title block, the per-person summary, the people × days grid and a Legend sheet. "Excel, this month" uses what is on screen; "Excel, every month" walks from `firstAttendanceMonth()` to now. Status colours are derived from `STATUS_TONE`, not written out again, and are applied as conditional formatting so an edited letter recolours itself.
* Console (`pages/Attendance.jsx`, `PAGES`): Team = Today, Register, Corrections, Leave requests / calendar / balances, QR code (`pages/attendance/QrCodeDisplay.jsx`, with a full-screen navy kiosk for the gate; `?full=1` opens straight into it); My records = My attendance, My leave, My payslips; the attendance and leave rules are in the Control centre (`/control?section=attendance`, Super Admin). Pending corrections and leave requests show as counts. The live-code logic is `hooks/useGateCode.js` and who may see the code is `canShowGateCode` in `pages/attendance/gate.jsx`, both shared with the Dashboard's gate card. **The Dashboard card never fetches the code on view** (`useGateCode({ live: false })`: `attendance_qr_show` rotates the token and records the viewer, a write); it shows the station, today's count and the last scan, and starts the code on "Show gate code". Who is expected today (always-present people, leave, weekly off, holidays) is one rule in `lib/attendanceToday.js` (tested), used by Today, the Dashboard and the QR page. My attendance and the day drawer show the database's `worked_min` (`dayView` in `pages/attendance/format.js`), punches only while a day is still running. Late marks count only by `countsAsLate` (0068). `lib/attendance.js` is GENERATED from `Ortex.Mobile/src/domain/attendance.ts`: edit the TS side.
* **Payroll** (0040, modelled on Zoho Payroll India): `/payroll`: Overview, Pay runs, Employees, Approvals, Loans, Reports; its settings sit in the Control centre (Super Admin). Access is `is_payroll()`, never `is_admin()`. PAN and bank account are encrypted with a Vault key; the table keeps only the last four digits. Pay runs go draft -> pending approval -> approved -> paid; a regular run cannot be submitted or approved until its month's attendance is locked (`payroll_run_transition`, 0065, and the run screen). Calculate refuses when `attendance_month_summary` cannot be read (`payableFrom` in `lib/payroll.js`) instead of paying full months; a person with no attendance row is paid the full month but flagged `attendanceMissing` on the slip. A payslip is visible to its employee only once paid. Not yet run end to end with real salaries.

## Design system (Keystone / Metronic port)

Tokens in `src/index.css` (Tailwind v4 `@theme` over HSL vars); kit in `components/ui/Ui.jsx`.

* **Flat surfaces**: every `--shadow-*` token is `none` except the two overlay tokens (1px ring). Never add an in-page `shadow-*`.
* **Semantic utilities only** (`bg-card`, `text-muted-foreground`, `text-warning-text`, `bg-success/12`, `squircle`, ...). Never raw Tailwind hues or hex.
* **Buttons: exactly three sizes** via `size` on `Button`: `sm` 30px, `md` 40px (default), `lg` 50px; `icon` for square. Never override height, text, padding or radius from a page. Every button carries `squircle`.
* **Tables**: `mt-head` on `<thead>` and `mt-body` on `<tbody>`, always both; the V2 lists (Leads, Quotations) use the `v2-head` / `v2-body` pair instead (34px uppercase head, 56px rows). Those rules are unlayered CSS and beat Tailwind utilities, so padding/weight classes on a `<th>` do nothing. Horizontal rules only.
* **Overlays and fields**: `Drawer` and `Modal` are real dialogs through `useDialog` (role, focus moved in, trapped and restored, Escape closes only the topmost overlay); pass `dirty` from a form so closing asks "Discard your changes?". `Field` ties its label, hint and error to the control with `useId`, so a control inside `Field` needs no `id` of its own. Type tokens `text-meta` (11px), `text-caption` (12.5px), `text-ui` (13px), `text-title` (15px) replace one-off `text-[…]` sizes in new code. A guarded route without access shows a "You do not have access" notice naming the module, never a silent redirect.
* **Form controls**: one `CONTROL` class backs `Input`, `Textarea`, `Select` (45px). `Select` is a portal-rendered listbox that still takes `<option>` children and calls `onChange({ target: { value } })`. `searchable` adds a filter box to it (an `<option data-search>` adds words to match); `onCreate(text)` + `createLabel(text)` add a row that takes what was typed when it matches nothing, and `valueLabel` is what the closed control then reads. The quotation and invoice line-item picker uses all four, so an item that is not in the catalogue is named in the picker itself (as the phone app's `LineItemSheet` does).
* **List-page toolbars**: `ChipGroup` filters left; right-pinned `SearchInput` then `ToolbarButton` / `ExportButton` (both 45px from `TOOLBAR_SHAPE`). Title and primary create button live in the table's `CardHeader`. Reference: `pages/Invoices.jsx`. The V2 lists use `components/sales/ListParts.jsx` instead (smart views, 34px toolbar, `ActionMenu`, `StatusDropdown`, `Pager`), with the `line` colour token (#E3E6EC) for outlines.
* `Tabs` is the hub-level underline switch; `PillTabs` is for a sub-tab row on the canvas.
* Icons: Iconsax via `components/ui/Icons.jsx`, `Bulk` variant everywhere except the header (`Linear`).
* App icons: `public/icons/app-icon-1000.png` is the master; `npm run icons` generates the rest (never hand-edit). No service worker yet.
